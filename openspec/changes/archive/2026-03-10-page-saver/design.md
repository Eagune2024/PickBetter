## Context

PickBetter 是一个基于 AI 的网页元素修改工具,用户可以选择页面元素并通过自然语言指令进行修改。目前用户在完成修改后无法保存结果,所有更改在页面刷新或关闭后都会丢失。

为了解决这个问题,我们需要实现一个完整的页面保存功能,参考 SingleFile 扩展的实现方式,将当前网页状态(包括 AI 修改后的 DOM)序列化为单个自包含的 HTML 文件。

**当前架构约束:**
- Content Script 必须打包为 IIFE,不支持 ES Module
- 使用消息驱动模式在 Background 和 Content Script 之间通信
- 所有类型定义使用 TypeScript,确保类型安全
- 需要跨浏览器兼容(Chrome、Firefox)

## Goals / Non-Goals

**Goals:**
- 实现完整的页面序列化和保存功能,支持 DOM、CSS、图片等所有资源的内联化
- 在 AI 修改完成后提供直观的"保存页面"按钮
- 提供进度反馈,优化大页面的保存体验
- 确保跨浏览器兼容性
- 优雅处理 CORS 限制和其他边缘情况

**Non-Goals:**
- 不实现编辑功能(如 SingleFile 的注释和删除功能)
- 不实现自动保存功能
- 不实现云存储集成(如 Google Drive、GitHub 上传)
- 不支持保存多个标签页(仅保存当前标签页)

## Decisions

### 1. 模块化架构设计

**决策:** 将页面保存功能拆分为多个独立的处理器模块,每个模块负责特定的资源类型。

**理由:**
- **关注点分离**: 每个模块专注于单一职责,易于测试和维护
- **可扩展性**: 未来可以轻松添加新的资源类型支持
- **可复用性**: 处理器可以独立使用或组合使用

**模块划分:**
```
source/utils/pageSaver/
├── index.ts                 # PageSaver 主入口,协调所有处理器
├── dom-processor.ts         # DOM 处理器: 克隆、序列化、Shadow DOM、Canvas
├── css-processor.ts         # CSS 处理器: 提取、内联、URL 转换
├── image-processor.ts       # 图片处理器: Base64 转换、懒加载处理
├── font-processor.ts        # 字体处理器(可选): @font-face、web fonts
├── resource-fetcher.ts      # 资源获取器: fetch、缓存、CORS 处理
├── html-generator.ts        # HTML 生成器: 组装最终 HTML、触发下载
└── types.ts                 # 类型定义
```

### 2. 资源获取策略

**决策:** 使用浏览器原生 `fetch` API 获取外部资源,实现缓存机制避免重复下载。

**理由:**
- **无需外部依赖**: 使用浏览器原生 API,不增加包体积
- **类型安全**: 通过 TypeScript 封装,确保返回类型安全
- **性能优化**: 缓存机制避免重复下载相同资源

**替代方案考虑:**
- ❌ **使用 XMLHttpRequest**: 过于老旧,不如 fetch 现代化
- ❌ **通过 Background Script 代理**: 增加复杂度,且 Content Script 的 fetch 已足够
- ❌ **引入第三方库(如 axios)**: 增加依赖,原生 fetch 已满足需求

### 3. CSS 内联化策略

**决策:** 采用"提取 → 合并 → 转换"的三阶段策略处理 CSS。

**具体步骤:**
1. **提取**: 收集所有 `<style>` 标签内容和外部 CSS 文件
2. **合并**: 将所有 CSS 合并为单个 `<style>` 标签
3. **转换**: 处理 CSS 中的相对 URL、CSS 变量、`@import` 规则

**理由:**
- **简洁高效**: 单个 `<style>` 标签便于管理
- **保持语义**: 保留 CSS 规则的原始结构和优先级
- **兼容性好**: 不依赖复杂的 CSS 解析器

**CSS URL 处理:**
```typescript
// 将相对 URL 转换为绝对 URL
url(../images/bg.png) → url(https://example.com/images/bg.png)
```

### 4. 图片处理策略

**决策:** 使用 `FileReader API` 将图片转换为 Base64 data URI,实现缓存和去重。

**处理范围:**
- `<img src="...">` 标签
- CSS `background-image` 属性
- `<picture>` 元素和 `srcset` 属性
- SVG 中的 `<image>` 元素
- 懒加载图片(`data-src` 属性)

**资源去重:**
```typescript
// 使用 data URI 的 hash 作为 key
const resourceMap = new Map<string, string>();
function hashDataURI(dataURI: string): string {
  const data = dataURI.split(',')[1]?.slice(0, 100) || '';
  // 简单 hash 算法
}
```

**理由:**
- **自包含**: Base64 编码使图片嵌入 HTML,无需外部文件
- **去重优化**: 相同图片只保留一份,减小文件体积
- **懒加载支持**: 处理现代网页常见的懒加载技术

### 5. 高级元素处理策略

**决策:** 对 Shadow DOM、iframe、Canvas 等复杂元素采用渐进式处理,失败时优雅降级。

**处理方式:**
- **Shadow DOM**: 序列化后插入到 host 元素内
- **iframe**: 仅处理同源 iframe,跨源 iframe 保留原始引用
- **Canvas**: 转换为 `<img>` 标签,使用 `toDataURL()` 获取图片
- **SVG**: 保留原始 SVG 代码,处理内部引用的资源

**理由:**
- **兼容性**: 不是所有网页都使用这些技术,但需要支持
- **渐进增强**: 基础功能优先,高级功能逐步添加
- **优雅降级**: 处理失败时保留原始内容,不中断整个流程

### 6. 进度反馈机制

**决策:** 在保存过程中提供实时进度反馈,显示当前处理的阶段和百分比。

**进度阶段:**
1. 正在克隆 DOM...
2. 正在处理 CSS (3/10)...
3. 正在转换图片 (15/42)...
4. 正在优化资源...
5. 正在生成 HTML...

**实现方式:**
- 在 AI 对话框中显示进度条和文本提示
- 使用异步队列分批处理,避免阻塞 UI
- 处理完成后显示"保存成功"或失败原因

**理由:**
- **用户体验**: 大页面处理可能需要几秒,进度反馈避免用户焦虑
- **透明度**: 让用户了解当前处理状态
- **错误定位**: 如果失败,用户知道在哪个阶段出错

### 7. 文件命名策略

**决策:** 默认使用"页面标题-时间戳.html"格式,支持用户自定义。

**格式:**
```typescript
const filename = `${document.title.replace(/[^\w\s]/gi, '')}-${Date.now()}.html`;
```

**理由:**
- **可读性**: 包含页面标题,易于识别
- **唯一性**: 时间戳确保文件名不冲突
- **灵活性**: 用户可以重命名,或未来添加自定义选项

### 8. CORS 限制处理

**决策:** 对 CORS 限制采用"尝试获取 → 失败时跳过"的策略,记录警告但不中断流程。

**实现:**
```typescript
async function safeFetch(url: string): Promise<string | null> {
  try {
    const response = await fetch(url);
    if (!response.ok) throw new Error('Not OK');
    return await response.text();
  } catch (error) {
    console.warn(`无法加载资源(可能是 CORS): ${url}`);
    return null; // 返回 null,继续处理其他资源
  }
}
```

**理由:**
- **不依赖外部服务**: 不通过代理服务器绕过 CORS
- **用户友好**: 部分资源失败不影响整体功能
- **透明度**: 通过 console 记录失败信息,便于调试

## Risks / Trade-offs

### 性能风险

**风险:** 大页面(如包含大量图片的网页)处理时间较长,可能导致浏览器卡顿。

**缓解措施:**
- 使用 `requestIdleCallback` 或分批处理,避免阻塞主线程
- 实现进度反馈,让用户知道正在处理
- 设置超时机制,避免无限等待
- 考虑使用 Web Worker(如果性能问题严重)

### 内存占用风险

**风险:** 图片转换为 Base64 后内存占用增加,可能导致内存溢出。

**缓解措施:**
- 实现资源去重,相同图片只保留一份
- 使用流式处理,避免一次性加载所有资源
- 设置内存上限,超过时提示用户
- 提供"仅保存 DOM"选项,跳过图片转换(未来可扩展)

### CORS 限制风险

**风险:** 某些外部资源(如字体、CORS 图片)无法通过 fetch 获取,导致保存不完整。

**缓解措施:**
- 记录所有获取失败资源,在控制台输出警告
- 在最终 HTML 中添加注释,标注哪些资源未能保存
- 提供"保存诊断信息"功能,帮助用户了解问题
- 文档说明 CORS 限制,设置合理期望

### 浏览器兼容性风险

**风险:** 某些 API 在不同浏览器中行为不一致。

**缓解措施:**
- 优先使用标准 API,避免实验性功能
- 在 Chrome 和 Firefox 中充分测试
- 使用 `webextension-polyfill` 确保跨浏览器一致性
- 提供特性检测,不支持时优雅降级

### 文件体积风险

**风险:** 保存后的 HTML 文件可能很大(几 MB 到几十 MB),影响分享和存储。

**缓解措施:**
- 实现 CSS 压缩(移除注释、多余空白)
- 考虑图片压缩(可选项,未来扩展)
- 在文件名中显示文件大小,让用户有预期
- 文档说明大文件的处理建议

## Migration Plan

### 部署步骤

1. **阶段 1: MVP 实现**
   - 实现 DOM 克隆和基础序列化
   - 实现 `<img>` 标签的 Base64 转换
   - 实现基础 CSS 内联(`<style>` 标签)
   - 验证核心流程可行性

2. **阶段 2: 增强功能**
   - 添加外部 CSS 文件处理
   - 添加 CSS 背景图处理
   - 添加 `srcset` 和懒加载支持
   - 实现资源缓存和去重

3. **阶段 3: 高级功能**
   - 添加 Shadow DOM 支持
   - 添加 iframe 处理
   - 添加 Canvas 转换
   - 添加字体内联(可选)

4. **阶段 4: 优化和完善**
   - 性能优化和进度反馈
   - 错误处理和边缘情况
   - 用户文档和测试

### 回滚策略

- 功能完全独立,不影响现有代码
- 如果出现严重问题,可以通过移除"保存页面"按钮快速回滚
- 不涉及数据迁移,无回滚风险

## Open Questions

1. **是否需要支持选择性保存?** (如仅保存特定区域、排除某些元素)
   - 当前决定: 否,保存整个页面
   - 未来可扩展: 添加用户选择保存范围的功能

2. **是否需要压缩保存的 HTML?** (如使用 gzip 压缩)
   - 当前决定: 否,保持纯文本格式
   - 未来可扩展: 提供"压缩保存"选项

3. **是否需要保存历史记录?** (如保存过的页面列表)
   - 当前决定: 否,仅提供一次性保存功能
   - 未来可扩展: 在 Options 页面添加历史记录

4. **如何处理动态生成的内容?** (如通过 JS 定时更新的内容)
   - 当前决定: 保存触发时刻的 DOM 快照
   - 未来可扩展: 提供"等待内容加载完成"选项
